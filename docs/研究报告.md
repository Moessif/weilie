# 「围猎」——基于普通安卓手机的多人在途基站覆盖边界协同实测系统

## 研究报告

**参赛赛事**：中国人民公安大学第三届学生科技应用创新大赛（科技制作与技术应用类 · 公安网络通信与移动应用关键技术方向）

**备选名称**：蜂巢猎影、基站围界

## 摘要

在公安实战中，上级机关往往只能向基层民警提供目标基站的编号类参数（ECI / NCI / LAC+CI，或经纬度+粗略半径），而基层单位普遍缺乏专用路测仪、扫频仪等高级装备，难以把「以基站为圆心、半径可达 1 公里的粗略范围」快速收敛为可行动的精确覆盖边界。本项目面向这一痛点，研制「围猎」系统：在**免 root、无专用设备**的前提下，使用普通安卓手机完成目标基站覆盖边界的多人在途协同实测。系统支持四种上级参数格式的智能解析建任务；通过 TelephonyManager 免 root 采集服务小区与邻区的 RSRP/RSRQ/SINR 及 GPS 打点数据，支持双卡分卡采集与 5G NSA 制式识别；采用「内点凸包→米制缓冲带→IDW 插值→Marching Squares 等值线→置信度评估」的多源融合拟合算法，把走测样本转化为带置信度的覆盖边界与热力图；内置取证相机，拍照即在照片上烧录时间、地址与双卡蜂窝参数水印，并首创影像验真机制——照片落库即算 SHA-256 登记至自建服务，服务端签发 8 位验证码与 HMAC-SHA256 签名，任何第三方扫码即可独立核验照片未被修改且确由某设备某时某地登记；依托 WebSocket 实现队长划区、队员分片围测、数据实时汇聚的多人协同作业；并提供 CSV/GeoJSON/KML 导出与基于 DeepSeek 大模型的受控 AI 助手。全系统坚持合规红线：全自研代码、权限最小化（不申请 READ_PHONE_STATE）、不涉及锁网锁频/测速/KPI/信令解码等敏感能力。本研究报告从背景需求、现状对比、系统设计、关键技术创新、试验设计与合规伦理等方面完整阐述本作品。

**关键词**：基站覆盖测量；移动通信；协同定位；凸包算法；IDW 插值；等值线拟合；取证水印；影像验真；Android；公安信息化

## 一、背景与需求分析

### 1.1 实战痛点：基层无高级装备条件下的覆盖定位难题

在侦查办案、大型活动安保、应急处突等场景中，确定目标手机所在基站的真实覆盖范围，是划定侦查范围、部署盘查力量、缩小搜捕圈的关键环节。然而该环节在基层长期存在「三无」困境：

1. **无装备**。专业路测仪（如 TEMS、QXDM 系列装备及配套软件）单价从数万元到数十万元不等，扫频仪更为昂贵，一般只有省级或市级的专门技术部门才配备，县分局、派出所一级基本处于「空白」状态。
2. **无数据**。基站工程参数、扇区方位角、电子下倾角、发射功率等属于运营商内部资料，向基层民警开放受限；上级技侦或运营商能够提供的，通常只是目标小区的标识参数与一个粗略的覆盖半径估计——而这个半径在城区可能高达 1 公里，覆盖数万乃至数十万平方米。
3. **无方法**。面对一个 1 公里半径的圆形参考区，传统做法要么「撒网式」排查（人力消耗大、暴露风险高），要么凭经验目测（误差不可控、难以复盘）。缺乏一种把「粗略参数」快速、可量化地收敛为「可行动边界」的轻量技术手段。

与此同时，几乎每名民警随身携带的智能手机本身就是一台「移动信号测量终端」——它持续接收所在与服务小区广播的小区标识与信号强度。**让普通手机成为测量仪器，让多名民警的走测样本汇聚为覆盖边界**，正是本作品要回答的问题。

### 1.2 需求定义

基于上述痛点，本作品将用户需求固化为一条完整作业链：

> **接收上级参数 → 建立测量任务 → 多人分片走测 → 覆盖边界收敛 → 置信度评估 → 导出上报。**

对每个环节提出明确的约束条件：

- **输入环节**：上级参数格式不统一，可能以 ECI、NCI、LAC+CI、经纬度+半径任意一种（或其变体：十六进制、带 MCC-MNC 前缀、全半角混杂）给出，系统必须做到「贴进来就能解析」；
- **采集环节**：目标人群手机不 root、不拆机、不外接设备；现场可能信号不佳，采集须本地持久化、断点可用；
- **分析环节**：样本是离散的走测打点，必须输出连续的边界（不是散点），且必须给出「这个边界可信到什么程度」的量化结论；
- **协同环节**：四至八人的围测小组需要实时共享位置、样本与现场照片，队长需要能划分子区域并掌握整体进度；
- **输出环节**：结果要能进入既有 GIS 流程（CSV/GeoJSON/KML），供指挥调度系统直接使用。

## 二、国内外现状

### 2.1 专业网优路测软件

以 TEMS Investigation、QXDM/QualiPoc、珠海世纪鼎利 Pilot 系列等为代表的商用路测软件，是运营商网络优化的标准工具。它们功能极为完备：支持全制式（GSM/TD-LTE/FDD-LTE/NR）信令采集、层三信令解码、自动测试计划（含拨打测试）、KPI 统计与报告生成等。但其定位与公安基层实战存在显著错位：

| 维度 | 专业路测软件 | 本作品「围猎」 |
|---|---|---|
| 目标用户 | 运营商网优工程师 | 基层办案民警 |
| 硬件要求 | 专用测试终端/扫频仪/有root测试机 | 普通安卓手机，免 root |
| 价格 | 数万至数十万元 | 免费自研 |
| 使用门槛 | 需专业培训 | 向导式操作+普通/专家双模式 |
| 多人协同 | 无（单人单机） | 核心能力：分片围测、实时汇聚 |
| 输出形态 | 网优报告、KPI 图表 | 可行动的覆盖边界（GIS 可用） |
| 合规属性 | 涉及信令解码等受控能力 | 主动规避敏感功能，纯物理层观测 |

国内亦有团队尝试将众包思路引入网络质量评估（如运营商投诉定位、第三方信号众包应用 Network Cell Info Lite、CellMapper 等），但这类工具要么止步于「信号地图展示」，要么服务于全球基站数据库共建，均未针对「给定目标小区、快速收敛覆盖边界、支撑围捕决策」这一具体任务建模，也缺乏多人实时协同与置信度评估能力。

### 2.2 本作品的定位差异

综上，本作品并非再造一个「简化版路测软件」，而是开辟了一条差异化路线：**面向单一任务（覆盖边界实测）、面向特定群体（无装备基层民警）、面向协同作业（多人分片围测）** 的轻量专用系统。在功能上做减法（不做测速、KPI、测试计划、信令解码），在协同与算法上做加法（分片围测调度、边界拟合、置信度量化）。

## 三、系统设计

### 3.1 总体架构

系统采用「端—云」两层架构、端侧五层分层的总体设计：

- **采集层**（Android 端）：TelephonyManager 免 root 采集服务小区与邻区信息（CI/PCI/EARFCN/RSSI/RSRP/RSRQ/SINR），融合 GNSS 定位，毫秒级时戳打点，JSONL append-only 落盘；
- **数据层**（Android 端）：会话级 JSONL 文件 + manifest 索引，天然满足「测量证据不可篡改」的 append-only 语义，规避了 Room/KSP 的构建复杂度，后续可平滑迁移 Room；
- **算法层**（Android 端，纯 JVM 可单测）：凸包计算、多边形缓冲带、IDW 插值热力网格、Marching Squares 等值线提取、16 扇区方向覆盖度统计与置信度合成，全部实现为无 Android 依赖的纯 Kotlin 模块；
- **呈现层**（Android 端）：Jetpack Compose 构建的双模式界面——普通模式以信号条与白话时间线呈现，专家模式展开全部工程参数；地图层经 MapEngine 抽象，内置 Canvas 迷你地图兜底，百度 SDK 接入点预留（用户自备 key）；
- **协同层**（服务端）：Kotlin Ktor 2.3.x + WebSocket，内存态房间 + JSON 快照持久化；已部署于阿里云 ECS（2 核 4 G，Ubuntu 24.04，systemd 托管，另提供 docker-compose 一键部署方案），健康检查 `/api/health`；队长建立房间、划定分区，队员加入后位置/打点摘要/照片实时同步，支持文字图片聊天；同一服务端承载照片验真登记与核验接口。

数据流上，一条打点样本的完整旅程为：**传感器采集 → 会话 JSONL 追加 → 拟合引擎增量触发 → 边界/热力/置信度更新 → 本地渲染 + WebSocket 广播至队友端 → 会话结束导出 CSV/GeoJSON/KML**。

### 3.2 模块划分

Android 端按 `com.gakj.weilie` 包划分为以下核心模块：

| 模块 | 职责 | 关键类 |
|---|---|---|
| `core.parsing` | 四格式任务参数解析与归一化 | `TaskInputParser` |
| `core.collect` | 免 root 采集引擎、定时打点调度 | TelephonyManager 封装 |
| `core.model` | 目标小区/样本记录/制式枚举等领域模型 | `TargetCell`、`SampleRecord`、`Rat` |
| `core.fitting` | 覆盖边界拟合全流水线 | `CoverageFitter`、`ConvexHull`、`PolygonBuffer`、`IdwInterpolator`、`MarchingSquares`、`DirectionCoverage` |
| `core.storage` | JSONL append-only 会话存储与 manifest | 会话仓库 |
| `ui.*` | Compose 双模式界面、任务向导、法律声明 | 各 Screen/ViewModel |
| `map.*` | MapEngine 抽象与 Canvas 兜底渲染 | 地图适配器 |
| `collab.*` | WebSocket 客户端、房间/分区/消息 | 协同控制器 |
| `ai.*` | DeepSeek 适配器、白名单域守卫 | AI 助手 |

在上述模块之外，端侧还包含三类功能模块：**取证相机**（全屏 CameraX 拍摄与双段水印烧录）、**影像验真**（照片哈希登记、验证码/二维码展示、在线三重核验与离线补登队列）与**双卡小区规划**（`SimCellPlanner` 按订阅卡规划小区来源，`CellCodec` 负责 NCI/ECI 编号编解码与分解展示，两者均有独立单元测试覆盖）。

服务端为独立工程 `server/`，以房间（Room）为聚合根管理成员、分区、位置流与打点摘要，并承担照片验真注册表（JSONL 追加写）与登记/核验接口。

### 3.3 双模式界面与主题系统设计

考虑到使用者的专业背景差异，界面在信息呈现上做了严格的双轨设计：

- **普通模式**：以「信号强弱条 + 白话时间线」呈现（如「14:32 走到路口，信号变好」），不出现任何需要培训才能理解的参数；
- **专家模式**：完整展开服务小区/邻区的全字段工程参数（EARFCN、PCI、RSRP/RSRQ/SINR、时戳），供有通信背景的使用者核查原始观测；
- **主题系统**：提供明亮/暗色/跟随系统三种外观模式，内置 10 个预设主题色并支持自定义色相与饱和度，选中即生效并持久化保存——兼顾夜间执勤的低亮环境与白天强光下的屏上可读性。主题适配层同时覆盖地图、聊天浮泡、扫码、AI 助手四个深浅色易失衡的高危界面，并通过 `values-v31` 主题把 Android 12+ 冷启动画面背景固定为深色（`#0B1020`），消除系统默认的白闪。

### 3.4 取证相机与影像水印设计

现场取证是覆盖测量的伴生需求：边界结论需要现场照片佐证，而照片本身也应成为经得起核查的证据。系统内置全屏 CameraX 取证相机，实现「拍摄即取证」：

- **双段水印烧录**：拍照即刻在照片左下角烧录两段信息——第一段为大字时间，辅以日期、星期、经百度 SDK 本地逆地理编码得到的地址，以及可编辑的地点备注；第二段为现场蜂窝数据块，按每张 SIM 卡逐卡列出运营商、制式与频段、NRARFCN/EARFCN、PCI、NCI/ECI（含 gNB-CID/eNB-CID 分解式）、RSRP、SINR，使照片自带不可分离的现场通信环境快照；
- **取证对象分类**：相机内可选 5 类取证对象——普通取证、隐蔽摄像头、可疑摄像头、可疑设备、其他；
- **地图标点回看**：拍摄完成后，系统即刻按 GPS 位置在地图上落下对应类别的「标点」，点击标点即可回看照片与拍摄时刻的现场数据，形成「照片—位置—通信环境」三位一体的取证链。

## 四、关键技术与创新点

### 4.1 创新点一：四种上级参数格式的容错智能解析

实战中上级参数的「脏」程度远超想象：全角半角混杂、中英文冒号混用、十六进制与十进制并存、有或没有制式标签、有或没有 MCC-MNC 前缀。`TaskInputParser` 实现了对以下四类格式的统一容错解析：

1. **ECI**（LTE 小区标识，28 bit）：支持 `ECI 217546496`、裸十进制、`0x0CF7A40` 十六进制、`0CF7A40H` 后缀式十六进制、`460-00-217546496` 带 MCC-MNC 前缀五种变体；
2. **NCI**（NR 小区标识，最大 36 bit）：支持带标签与裸数字，超 28 bit 的值自动按 NCI 处理，超 36 bit 给出「请核对」警告；
3. **LAC+CI**（2G/3G）：支持 `LAC 12345 CI 67890`、`12345-67890`、`LAC:12345,CI:67890`，并以「LAC ≤ 65535」等启发式规则消解破折号格式的歧义；
4. **经纬度+半径**：支持 `31.2304,121.4737,500m`、`31.2304 121.4737 半径500` 等写法，缺半径时给出「默认按 1000 m 展示参考圆」的白话提示而非静默失败。

解析前先做 NFKC Unicode 归一化（全角字母数字符号转半角）与中文标点统一，解析后对 ECI 自动拆解出 eNodeB 标识（高 20 bit）与小区 CID（低 8 bit）辅助人工核对；按位数启发式推断制式（>2²⁸ 视为 NCI，>2¹⁶ 视为 LTE ECI）；解析失败时输出人话错误与已识别部分，绝不抛出技术性异常。这一「贴进来就能建任务」的体验直接决定了系统在高压作业环境下的可用性。

### 4.2 创新点二：免 root 普通手机的多制式信号采集

采集引擎仅依赖公开 API `TelephonyManager.getAllCellInfo()`，即可同时获取服务小区与邻区列表的小区标识（CI/NCI/PCI）、频点（EARFCN/ARFCN/NRARFCN）与信号质量（RSRP/RSRQ/RSSI/SINR），配合 GNSS 定位以毫秒时戳完成时空打点。全程不申请 `READ_PHONE_STATE` 权限，不使用任何反射/隐藏 API/root 通道。针对 Android 版本差异（各制式 CellInfo 子类字段可用性不同）做了逐制式适配与字段降级策略，并以真机摸底试验（≥3 部机型）验证邻区可用性——这一「低成本传感器化」路径是整个系统成立的前提。

在多卡与 5G 组网上，采集链路进一步实现**双卡分卡采集与 5G NSA 识别**：以 `createForSubscriptionId` 按订阅卡分别获取各卡的小区信息，避免双卡数据串扰；取材上 NR 优先，不足时用 LTE 小区信息中的 NR 邻区补齐 NR 行；对个别 ROM 在 `getAllCellInfo()` 中过滤掉 NR 小区的机型，以 `dataNetworkType` 兜底判定并标注 `NR(NSA)`，保证 5G 场景不漏测。编号语义层面，`CellCodec` 将 36 bit NCI 按「gNB 标识 ×4096 + 12 bit CID」分解、28 bit ECI 按「eNodeB 标识 ×256 + 8 bit CID」分解，同一编号同时提供十进制、十六进制与分解式（如 `5677244420(1386046-4)` 的用户习惯写法）三种展示，供不同使用习惯的办案人员核对。

### 4.3 创新点三（核心）：多源融合的覆盖边界拟合算法

离散走测样本如何变成连续、可信、可行动的覆盖边界，是本作品的算法核心。`CoverageFitter` 实现了五级流水线：

**（1）样本过滤与内点筛选。** 剔除无 RSRP 或 GPS 精度半径大于 60 m 的不可用样本（无精度标注时保留并按 10 m 计）；以可配置的 RSRP 阈值（默认 −110 dBm，共 6 档可配，借鉴 CellularPro 的 6 档评级思路）筛出「处于覆盖内」的内点观测；内点不足 3 个时退化为全样本拟合，总样本不足 8 个不启动拟合。

**（2）内点凸包。** 对内点坐标先以样本集质心为原点转换为米制局部坐标（避免经纬度在不同纬度的形变），再计算内点集的二维凸包，得到覆盖范围的「紧致骨架」。

**（3）米制缓冲带。** 考虑到凸包边界由有限样本支撑、边缘存在不确定性，对凸包做外扩缓冲：缓冲距离 = 基础缓冲 25 m + 平均定位精度 × 0.5。定位越差、缓冲越宽，将「测量不确定度」显式编码进边界几何——边界因此具备了自解释性。

**（4）IDW 插值与等值线提取。** 以 12 m 网格对全样本（含覆盖外样本）做反距离加权（IDW）插值，生成 RSRP 连续场；用 Marching Squares 算法在阈值电平上提取等值线闭环（过滤少于 4 点的碎片，保留最长的前 3 条），得到与凸包互补的「信号物理衰减视角」的边界。凸包回答「人到过哪」，等值线回答「信号到得了哪」，两者并陈供使用者交叉判读。

**（5）置信度评估。** 输出 0–100 分与低/中/高三档：

> **置信度得分 = 样本量因子 × 0.5 + 16 扇区方向覆盖度 × 0.5**

其中样本量因子 = min(1, 有效样本数 / 120)（120 个样本即饱和）；16 扇区方向覆盖度以凸包质心为原点将平面均分为 16 个扇区，统计内点落入的扇区比例——它直接度量「围测是否留有缺口」：哪怕样本量已饱和，若队员只走了半圈，方向覆盖度也会显著拉低置信度。得分 ≥ 70 且已覆盖 ≥ 12/16 扇区评为「高」，≥ 40 为「中」，否则「低」。这一模型把「采了多少」与「采得全不全」两个维度同时纳入，为指挥员提供可直接引用的量化决策依据。

**（6）双坐标输出与热力图。** 全部结果（凸包、缓冲带、等值线、热力网格）同时输出米制局部坐标与 WGS-84 经纬度两套，分别服务于算法内部与地图渲染/GIS 导出，热力网格同步换算为经纬度步长。

以上算法全部为无 Android 依赖的纯 JVM Kotlin 实现，配套单元测试覆盖几何构造、退化输入与边界条件，保证拟合逻辑可回归验证。

### 4.4 创新点四：多人协同的分片围测架构

单个手机走一圈耗时长且可能错过时机，「围猎」将作业模式升级为多人在途协同：队长创建任务房间后按方位划分子区域，队员分片「扫围」；WebSocket 通道实时同步各队员位置、打点摘要与现场照片，配以文字图片聊天；服务端以 Ktor 2.3.x 实现房间态管理，内存态运行 + JSON 快照持久化，docker-compose 单机一键部署。协同的价值不仅是「快」：多个方位的走测样本天然提升 16 扇区方向覆盖度，直接推高置信度——**协同模式与算法模型形成了正反馈闭环**，这是专业路测软件单人单机模式所不具备的。

### 4.5 创新点五：带白名单域守卫的 AI 助手

系统集成 DeepSeek v4.1 flash 云 API（适配器模式，可切换私有化端点），提供拍照场景分析（识别天线、楼宇遮挡等现场要素）与技术答疑。为守住合规与安全边界，AI 能力设计了「白名单域守卫」：仅放行与任务相关的提问域（信号判读、覆盖分析、操作指导），提示词层面拒绝与任务无关或敏感的话题，API key 由用户自配、不内置、不上传。这让 AI 增益与警务数据安全约束得以兼得。

### 4.6 创新点六：影像验真——可第三方独立复核的取证照片

现场照片一旦可能成为办案佐证，「照片有没有被改过」「是不是真在现场拍的」就会成为质证焦点。本作品设计了端云一体的**影像验真**机制，把可信性做进流程而不是事后声明：

- **登记签发**：拍照落库即刻计算文件 SHA-256，并登记至自建 Ktor 服务；服务端生成 8 位验证码，用 HMAC-SHA256 对「验证码+照片哈希+服务端时间戳+客户端时间戳+坐标」（签名原文 `code:sha256:serverTs:ts:lat:lon`）整体签名，登记记录以 JSONL 追加写方式存入服务端注册表，延续「证据不可篡改」的存储语义；
- **三重在线校验**：详情页展示验证码与 `WEILIE-VERIFY:<code>` 格式二维码。任何第三方扫码发起在线验证时，服务端同时校验三项——登记记录是否存在、图片哈希与登记值是否一致（照片被修改即失败）、签名是否有效（伪造登记即失败）。客户端「在线验证」按钮触发同一组校验，任一项失败即返回对应的中文失败原因（「记录未登记」「图片被修改」「签名无效」），现场可即时向第三方解释核验结果；
- **离线补登**：现场无网时照片先进入本地待登记队列，恢复联网后自动补登记，不因网络条件损失证据效力；
- **服务现状**：验真服务已随协同后端部署上线（`http://47.89.181.85:8080`，接口 `POST /api/photo/register`、`GET/POST /api/photo/verify`、`GET /api/photo/count`），签名密钥以 `600` 权限存放于服务器本地（`/opt/weilie/data/hmac.secret`），需纳入运维备份清单。

其论证口径经过刻意收敛：本机制**不是**「保证照片绝对真实」，**而是**让任何第三方都能独立验证「这张照片自登记以来未被修改，且确由某台设备在某时某地完成登记」——哈希锁定内容，HMAC 锁定登记行为，验证码与二维码供人复核。三者相互独立又互为印证，构成一条不依赖拍摄设备自身可信性的最小可信链。

> **【图 4-3 占位】影像验真流程图**——拍照→SHA-256→登记→HMAC 签发→二维码→第三方三重校验——来源：团队绘制【待绘制定稿】。

### 4.7 工程决策亮点

- **JSONL append-only 存储**：与「测量记录即证据」的语义天然一致，文件可逐行校验、不可静默改写，且规避 Room/KSP 构建风险；
- **纯 JVM 算法层**：凸包/缓冲/IDW/等值线/置信度全部可脱离设备做单元测试与回归验证；
- **地图引擎抽象**：无地图 key 时以内置 Canvas 迷你地图兜底，保证核心闭环（采集→拟合→呈现）不依赖任何第三方商业组件；
- **可回归的软件质量**：核心解析与算法层配套 **50 个单元测试全部通过**（编号编解码 `CellCodec` 9、参数解析 `TaskInputParser` 13+6=19、双卡规划 `SimCellPlanner` 12、拟合流水线 10）；客户端为单 APK 双架构（arm64-v8a + x86_64），minSdk 26 / targetSdk 35，工程基线清晰、可持续演进。

## 六、合规与伦理专章

本作品自立项起即将合规视为与功能同等重要的设计约束，以下五条红线贯穿全部开发环节：

1. **知识产权合规（全自研，路线 B）**：全部代码原创编写，不复制、不反编译任何第三方应用的源代码、so 库或资源文件。仅将 CellularPro 逆向分析得到的**参数字段词典**作为公开技术资料用于字段命名对照，并将 CellularPro 原版 base.apk 安装于同一测试机、同一小区下做**对拍金标准**——使用其「产物」（读数）而非其「本体」（代码）。
2. **权限最小化**：不申请 `READ_PHONE_STATE`。采集所用的 `getAllCellInfo()` 与 GNSS 定位均为无需敏感权限的公开 API，应用权限面收敛至定位、相机（拍照）、存储/网络等必要项。
3. **功能负面清单**：主动不做锁网锁频、测速、KPI 统计、测试计划（含自动呼叫）、信令事件解码等能力——它们要么触碰运营商网络完整性，要么涉及受控的信令层信息，均超出「覆盖边界实测」的任务必要边界。本系统只观测手机自身被动接收的广播信息，不注入、不干扰、不解码任何网络信令。
4. **数据安全**：测量数据仅存于本机会话文件与用户自建的协同服务器，不接入任何第三方数据平台；地图 key 用户自备；AI 调用走用户自配 key 且经白名单域守卫过滤。
5. **伦理与使用边界**：应用内置首次启动法律声明，明确本工具仅供依法执行职务的人民警察及经授权的培训教学场景使用，测量对象为基站信号这一物理现象本身，不针对、不识别任何个人通信内容。系统不存储、不传输任何通话、短信、用户身份类信息。

### 6.1 取证可信性专述：影像验真的合规论证

取证相机与影像验真功能引入后，本作品对「证据可信」的边界作出如下论证，供评审与实战检验：

1. **机制定位**：影像验真不承诺「证明照片绝对真实」，而是提供一条**可独立复核的最小可信链**——任何第三方无需安装本应用，扫描照片详情页二维码即可验证照片未被修改（哈希一致）、登记行为真实（HMAC 签名有效）、登记记录存在（服务端注册表可查）；
2. **证据语义**：验真回答的是「照片自登记起未被改动、确由某设备某时某地登记」，不回答「照片内容是否摆拍」——后者仍属办案人员职责，系统不越界代断；
3. **数据最小化**：登记内容仅含照片哈希、验证码、时间戳与坐标，不含照片本体与任何个人身份信息，符合数据最小化原则；签名密钥仅存于用户自建服务器本地（权限 `600`），不内置、不上传；
4. **边界一致性**：验真服务部署于用户自建服务器，与协同服务共用同一合规边界（自研、自运维、数据自持），不引入新的第三方数据通道。

## 七、结论与展望

「围猎」系统以「普通手机即测量终端、多名民警即传感器阵列」为核心思想，在免 root、零专用装备、全自研、权限最小化的约束下，完整打通了「上级参数解析 → 多人分片走测 → 多源融合边界拟合 → 置信度评估 → GIS 导出上报」的作业闭环。其贡献在于：

1. 提出并实现了面向公安实战的**多源融合覆盖边界拟合流水线**（内点凸包→米制缓冲→IDW 插值→Marching Squares 等值线→双因子置信度），把「人走过的范围」与「信号到达的范围」统一到同一坐标系下供交叉判读；
2. 设计了**16 扇区方向覆盖度**这一直接度量围测完整性的指标，并使其与多人协同作业模式形成正反馈；
3. 以**四格式容错解析**消除了上级参数格式壁垒，以**双模式界面**消除了使用门槛，以**五条合规红线**树立了同类工具的合规范式；
4. 设计并上线了**影像验真机制**（SHA-256 登记 + HMAC-SHA256 签名 + 验证码/二维码三重校验），使取证照片具备第三方可独立复核的可信性；配套双卡与 5G NSA 识别、取证水印相机与主题系统，系统由「测量工具」完善为「测量 + 取证」一体化的实战作业平台。

展望后续工作：其一，扩大真机机型矩阵，系统标定各品牌 CellInfo 字段差异；其二，引入扇区方位角先验与地形修正，进一步提升山区场景的边界精度；其三，探索与指挥调度系统的标准化对接（GeoJSON 服务化）；其四，在培训模式（录制回放）基础上构建实战化教学案例库，反哺公安教育训练；其五，为影像验真服务接入可信时间戳与公证存证通道，进一步提升证据链的司法可采性。
