## 四、详细发现

### 4.1 认证与会话（S3、M1、M4、L1、L2）

**S3 默认超级管理员口令可接管后台**

- 位置：`Application.kt:79-82`（`WEILIE_SUPERADMIN_PASSWORD ?: "admin12345"`）、`admin/AdminAuth.kt`（`mustChangePassword` 仅读取、无拦截点）。
- 影响：任何按默认配置部署的实例，攻击者用 `admin/admin12345` 即可获得超级管理员；即便修改了初始口令，`mustChangePassword` 标志也从未被用于阻断请求，「首登必改密」形同虚设。
- 修复：
  - 未配置环境变量时，改为**随机生成 18 位口令**并写入 `data/superadmin-initial-password.txt`（POSIX `rw-------`），控制台只打印文件路径；
  - `AdminSecurity.require()` 增加 `allowMustChange` 开关，默认在 `mustChangePassword=true` 时抛 `403 MUST_CHANGE_PASSWORD`；仅 `/auth/me`、`/auth/logout`、`/auth/change-password` 放行；
  - 改密成功后 `must_change_password` 置 0 并吊销该用户全部会话（强制重新登录）。

**M1 会话 Cookie 安全属性与传输安全**

- 位置：`admin/AdminAuth.kt:94-107`（`secure=false`）、`clearSessionCookie` 无属性、无 HSTS。
- 修复：新增 `cookieSecureFor(scheme)`（HTTPS 或 `WEILIE_COOKIE_SECURE=1` 时为 true），`appendSessionCookie` 与 `clearSessionCookie` 都使用它，保留 `HttpOnly` + `SameSite=Lax`。
- 未修：设备侧到服务端仍为明文 HTTP（见 M13，需要前置 TLS 反代，属部署改造）。

**M4 认证状态与设备绑定**

- `admin/AdminStore.kt:802-815`：`findClientToken` 未校验用户状态 → 已封禁/SUSPENDED 用户的令牌仍可用。修复：命中 `SUSPENDED/DELETED/LOCKED` 立即吊销令牌并返回 null。
- `:882-885`：`if (bound.isNotEmpty() && ...)` 条件短路，空 `deviceId` 可绕过绑定。修复：`if (bound.isNotEmpty() && provided != bound) 409 DEVICE_MISMATCH`。
- `:896-902`：客户端改密不吊销旧令牌。修复：事务内吊销全部 `client_tokens`。

**L1 会话绝对有效期**：`admin/AdminStore.kt:733-763` 仅有空闲超时。修复：`SessionRow.createdAt`，超过 12 小时（`SESSION_ABSOLUTE_MS`）自动吊销。

**L2 限流表上限**：`admin/AdminAuth.kt:130-157` 的 `failures` 无上限。修复：`LoginThrottle.purge(maxEntries=20_000)`（清过期项 + 按最近失败时间淘汰），并在 TTL 循环中定期调用。

### 4.2 授权与越权（S1、H1、H2）

**S1 角色批量赋值（Mass Assignment）→ 自提权**

- 位置：`admin/AdminStore.kt:555-592`（`createUser`/`updateUser` 直接写 `role`）、`admin/AdminRoutes.kt:230-241`（PATCH 仅 `requireWrite`）。
- PoC：组织管理员 `PATCH /api/admin/users/{自己的 id}`，正文 `{"role":"SUPER_ADMIN"}` → 直接成为超管。
- 修复：新增 `assertRoleAssignable(actor, role)`（超管可授任意；组织管理员仅可授 `USER`/`AUDITOR`；其它角色 403 `ROLE_FORBIDDEN`），并在 `createUser`、`updateUser`、导入用户路径统一调用；`updateUser` 额外禁止「非超管修改超管账号」与「修改自己的角色」。

**H1 管理站无角色门（BFLA）**

- 位置：`admin/AdminRoutes.kt:45-76` 登录不限制角色；`admin/AdminM2Routes.kt:239-477` 读接口仅 `require()`。
- 影响：任何拿到 App 账号的人都能登录后台，读取全站房间、成员实时坐标、照片原图、审计日志与激活码，并可继续利用邀请码进入房间。
- 修复：`AuthUser.canAccessAdminConsole`（`SUPER_ADMIN`/`ORG_ADMIN`/`AUDITOR`）+ 登录时校验；`/ops/status` 与 `PATCH /settings` 进一步收敛为超管专属。

**H2 跨组织签发激活码/重置码 → 接管账号**

- 位置：`admin/AdminStore.kt:645-703`（`issueCode`/`revokeCode` 无归属校验）、`admin/AdminRoutes.kt:244-261,358-365`；用户 id 自增可枚举（超管通常为 1）。
- PoC：组织管理员 `POST /api/admin/users/1/reset-password` 拿到明文重置码 → `POST /api/client/activate` 设置新口令 → 以超管身份登录。
- 修复：新增 `assertCanManageUser(store, auth, targetId)`，非超管对「超管账号」或「跨组织目标」一律返回 `404 用户不存在`（不泄露存在性）；接入 `POST/PATCH/DELETE /users`、`unbind-device`、`/codes`、`reset-password`。

### 4.3 房间协同（S2、S4、M2、L5）

**S2/S4 房间 WebSocket 身份与凭证**

- 位置：`RoomWs.kt:44-62`（身份/角色取自查询参数）、`:494-518`（同 userId 顶号且保留 CAPTAIN）、`:283-294`（`isCaptain = captainUserId == null || == msg.by`）、`:296-327`（任务区角色回退到客户端自报的 `qRole`）。
- 影响链：知道 `roomId` 即可自称任意 `userId`/`role`：顶掉真队长会话、自封队长下发/清除任务区、删除他人标点、读取全员精确 GPS。
- 修复（本轮）：
  1. `Zone`/`MarkerDelete` 的队长判定改为**只认服务端记录**（`room.members[myUserId]?.role`、`captainUserId == msg.by`），不再回退客户端声明；
  2. 入房校验邀请码：提供即比对（常量时间）、`WEILIE_REQUIRE_JOIN_CODE=1` 时缺失即拒、未强制时记录 `join_unverified` 审计；
  3. `RoomState` 增 `MAX_MARKERS=2000`、`MAX_ZONES=200`；`Marker` 字段长度截断（name 64 / note 200 / byName 64 / visibleTo 50）；聊天单条 500 字；单帧上限 1MB。
- 未修部分（见 5.1）：`WEILIE_REQUIRE_TOKEN` 仍未默认开启——因为当前 Android 客户端连接时不带 token/code，服务端强制会直接断掉线上 App。建议 App v1.13 携带 `code`（服务端已支持）后再把 `WEILIE_REQUIRE_JOIN_CODE=1` 打开。

**M2 房间令牌可自封队长**：`TeamRoutes.kt:74-108` 接受任意 `role`。修复：白名单只允许 `OBSERVER`/`MEMBER`，`CAPTAIN` 只能由服务端在「无队长」时自动提升。

**M3 邀请码强度**：`RoomStore.kt:148-154`（6 位数字、`kotlin.random.Random`）。修复：8 位、字符表去混淆（`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`）、`SecureRandom`；`/api/teams/by-code` 限流 60→10 次/分钟/IP 且加全局 600/分钟熔断；`rawCode` 限 4..16 位字母数字。**旧 6 位码仍可被 `findByCode` 命中**，线上已用真实房间验证兼容。

**L5 建房无上限**：`POST /api/teams` 仅按 IP 限流 10 次/分钟，仍可批量建空房。未修（需要按组织配额体系，计划随 H3 一起做）。

### 4.4 取证与文件（S5、H8、L3、L6）

**S5 照片上传可覆盖取证证据**

- 位置：`PhotoFiles.kt:83-110`（`POST /api/photo/upload` 匿名 + `REPLACE_EXISTING`）、`Application.kt:149`（未传 registry）。
- 影响：任何人拿到 `code` 即可覆盖原件，破坏「取证不可篡改」这一产品核心承诺。
- 修复：`photoFileRoutes(files, limiter, registry)`；上传时要求 `registry.byCode(code)` 存在（否则 404），并校验上传内容 `sha256` 与登记值一致（否则 409），幂等重传返回 200；另加 JPEG/PNG 魔数校验（`FF D8 FF` / `89 50 4E 47`）。

**H8 照片列表内存放大**：`admin/AdminM2Routes.kt` 分页前对每条记录 `readAllBytes`（最多 N×8MB）。修复：改 `exists`/`sizeOf` 读取元数据，不读原件。

**L3 验真上传异常回显**：`PhotoWebVerify.kt:391`。修复：对外固定文案「请求处理失败，请稍后重试」，异常细节只写日志；同时给 `/v/{code}`（120/min）、验真上传（10/min/IP）加限流。

**L6 照片登记接口**：`PhotoRegistry.register` 无鉴权、无字段长度限制。部分修复（上传侧已有完整性校验）；登记侧鉴权与 JSONL 轮转列入后续（见 5.5）。

### 4.5 注入与导出（H7）

- `ServerExports.kt:92-100`：CSV 的 `esc` 未中和 `= + - @` 前缀 → Excel 公式注入；KML 的 `esc` 是 JSON 转义，会把 `"` 变成 `\"` 破坏 XML。
- 修复：新增 `csvSafe()`（危险前缀加 `'`、超 500 截断、引号双写）与 `xmlEsc()`（`& < > " '` + 换行转空格），CSV/KML 全部改走新函数；`AdminM2Routes` 的审计导出同样处理。

### 4.6 运维面与信息泄露（M5–M10、M6、L4）

- `M6` `/admin/{path...}` 直接拼接 `admin/$path`：修复为 `safeAdminAssetPath()`（拒绝 `..`、反斜杠、绝对路径、控制字符；无扩展名走 SPA 首页），非法路径直接 400。
- `M7` `/metrics` 在配置了 `WEILIE_ADMIN_TOKEN` 时要求 `X-Admin-Token`（线上已验证 403）。
- `M8` `/ops/status` 收敛为超管专属；`PATCH /settings` 同样。
- `M9` 组织申请 `/organizations/apply` 加 5 次/分钟/IP。
- `M10` 客户端激活 10 次/分钟/IP + 全局 300/分钟熔断。
- `L4` 新增统一安全响应头插件：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Permissions-Policy`、`Cross-Origin-Opener-Policy: same-origin`；`/admin*` 与 `/v/` 追加 CSP（`script-src 'self'`、`frame-ancestors 'none'` 等）。
- `H6` 请求体上限插件：`Content-Length > 12MB` 直接 413 并中断（兼容 8MB 照片上传）。
- `H5` WebSocket 单帧上限 `Long.MAX_VALUE → 1MB`。

### 4.7 未发现问题的面（已逐项验证）

- **SQL 注入**：`admin/AdminStore.kt` 全部使用 `?` 绑定参数；动态 SQL 片段只来自静态常量与 `Long` 主键；`LIKE` 亦走绑定。
- **路径穿越**：照片/导出文件名均经 `^[A-Z0-9]{6,12}$` 白名单；`/admin` 静态资源已加白名单归一。
- **反序列化**：`WsMsg` 为 kotlinx `sealed` 白名单，无 Java 原生反序列化入口。
- **命令执行 / ZIP 解压 / 模板注入**：全工程无 `Runtime.exec`、无解压、无模板引擎。
- **管理站 XSS**：无 `v-html`、无 `innerHTML`、无 `document.write`；开放重定向仅接受单 `/` 开头；无 WebView/JS 桥。
- **堆栈泄露**：`StatusPages` 统一 500 兜底，不回显异常栈。
- **验真页 XSS**：`PhotoWebVerify.kt:64-73,164-184` 全部 `escapeHtml`。
- **密码学**：PBKDF2-HMAC-SHA256（210000 迭代、16 字节盐）、CSRF 常量时间比较、令牌/激活码/照片码均 `SecureRandom`。
- **客户端组件暴露**：Android `allowBackup=false`、组件基本 `exported=false`、隐式 Intent 均带 `FLAG_IMMUTABLE`、无自定义 TrustManager。

## 五、未修复项与理由

### 5.1 房间 WS 强制凭证（S2/S4 剩余部分）

服务端已支持 `code` 校验与 `WEILIE_REQUIRE_TOKEN`/`WEILIE_REQUIRE_JOIN_CODE` 开关，但**当前 Android 客户端连接 URL 不带 `code`/`token`**（`RoomClient.kt:85`）。若现在打开强制校验，线上全部 App 将无法进房。
**方案**：App v1.13 在连接串追加 `&code=<邀请码>`（服务端已实现校验），随后把 `WEILIE_REQUIRE_JOIN_CODE=1` 写入 systemd 环境，并给旧版本留一个版本下限判定。

### 5.2 房间/照片的组织隔离（H3）

`RoomStore` 没有 `orgId` 字段，`room_meta.org_id` 也从未写入，因此管理站无法把房间、照片按组织过滤。这属于**数据模型改造 + 存量数据回填**，不宜在夜间自动改；本轮只在管理站侧收敛了「谁能进后台」。
**方案**：房间创建时写入 `orgId`（App 端令牌已含组织），管理站列表按 `auth.orgId` 过滤，并给存量房间按邀请码归属回溯一次。

### 5.3 Android 本地登录校验（M14）

`AccountStore.kt:9-47` 明确注释「本期不做服务器校验，账号 ≥4 字符即视为登录成功」，属产品设计（离线可用）。它带来的风险是「导出/署名可伪造」。需产品决策：是否改为必须服务端登录、或对「署名」标注「本地账号」并在导出物中加离线标记。

### 5.4 计量与配额（L5、L8）

建房/基站查询的配额需要按组织维度计量，与本轮改动同属一个体系；当前以 IP 限流 + OpenCelliD 日上限 4500 兜底。

### 5.5 依赖升级（D1）

- `logback 1.5.12`：CVE-2024-12798/12801 仅在启用 janino 或外部配置时可用，本项目均不满足；建议升 `≥1.5.16`。
- `ktor 2.3.12`：CVE-2024-49580 与 `HttpCache` 插件相关，本项目未安装；建议升 `≥2.3.13`。
- `Netty 4.1.111`：CVE-2025-24970/55163 作用于 HTTP/2 与特定解码路径，本项目为明文 HTTP/1.1；建议升 `≥4.1.123`。
升级需要完整回归（WebSocket、multipart、静态资源），列入下一迭代。

### 5.6 TLS / HSTS（M1、M13）

生产为 `http://47.89.181.85:8080` 直连，无反向代理。加 TLS 需要域名证书 + Nginx/Caddy 前置 + App 端 `wss/https` 切换 + 删 `usesCleartextTraffic`，是一次**端到端发版**，不适合夜间无人验证时上线。本轮先把 Cookie `Secure`、CSP、安全头做好，并在服务端支持 `WEILIE_COOKIE_SECURE=1`，等反代就绪即可一键开启。

## 八、兼容性影响

- **旧邀请码**：6 位数字码仍可加入（`findByCode` 兼容），管理站列表照常显示。

- **管理站前端**：生产构建不再回退 mock 数据，接口异常时会如实报错（不再出现「演示数据看起来正常」的假象）。
