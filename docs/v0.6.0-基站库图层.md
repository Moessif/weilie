# v0.6.0 · 基站库图层与"以基站为中心划区"

> 本次新增两条能力：
> 1. **基站库图层**：接入开源众包库 OpenCelliD，在任务地图上显示附近的已知基站位置，并支持按 `MCC/MNC/LAC(TAC)/CellID` 精确查询某一基站；
> 2. **队长按基站划区**：队长在布置任务时先搜到某个基站，再以它为中心按"扇形 / 同心圈层"自动切分任务区域，逐块分配给队员。

---

## 一、为什么是 OpenCelliD

| 候选数据源 | 结论 |
| --- | --- |
| **OpenCelliD** | 社区众包、有公开 API、许可清晰（CC BY-SA 4.0）、中国有数据 → **采用** |
| BeaconDB（MLS 继任者） | 只有"用基站/WiFi 反查坐标"的接口，坐标被刻意混淆，无法用来打点 → 不用 |
| CellMapper | 只有 App/网页，无公开 API，抓取违反其 ToS → 不用 |
| 国内商业库（cellocation / 聚合数据） | 需付费、有 IP 封禁策略、许可不明 → 暂不接入 |
| GitCode "全国基站 LBS 定位库" | 静态快照（约 84 万行、截至 2019 年中），下载被拦 → 备选，未采用 |

**许可与署名（必须遵守 CC BY-SA 4.0）**：App 图层面板、查询弹窗、基站详情卡、队长划区弹窗底部均显示 `OpenCelliD · CC BY-SA 4.0 · https://opencellid.org`；接口返回体里也带 `source` 字段。对外演示、报告、答辩材料中引用基站库数据时需同样署名。

**精度声明（重要，别当成实测）**：OpenCelliD 的坐标来自众包上报，`samples` 多为 1、坐标量化到约 0.001°（百米级），室内/农村可能偏几百米。所以：
- App 内文案统一写"众包坐标，参考定位，非实测"；
- 详情卡显示 `samples` 与"精度"文案，不显示伪造的精确度；
- 测覆盖范围仍以**本 App 实测**为准，基站库只用来"找目标、定中心、给参考"。

## 二、服务端（weilie-server）

新文件 `server/src/main/kotlin/com/gakj/weilie/server/CellLibrary.kt`，注册在 `Application.kt`。

### 接口

| 方法 | 路径 | 参数 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/cells/near` | `lat`、`lon`、`r`（100–5000 m）、`limit`（1–1000） | 查附近基站，按距离升序 |
| GET | `/api/cells/cell` | `mcc`、`mnc`、`lac`（或 `tac`）、`cellid`（或 `ci`） | 按编号查单个基站 |
| GET | `/api/cells/stats` | — | 密钥是否配置、缓存瓦片数、今日上游调用量/上限 |

参数错误或上游失败时仍返回 HTTP 200，但 `ok=false` 且 `message` 是中文提示（App 直接 toast）。

`/api/cells/near` 返回示例：

```json
{
  "ok": true,
  "count": 5,
  "fetched": 0,
  "sites": [
    {"mcc":460,"mnc":1,"lac":6665,"cellid":110181241,"rat":"LTE",
     "lat":39.9011,"lon":116.3914,"rangeM":1000,"samples":1,"updatedSec":1577836800}
  ],
  "message": null
}
```

### 缓存与额度

- 上游按 **0.018° 瓦片**（纬度约 2 km，面积恒小于 OpenCelliD 的 4,000,000 m² 单次上限）拉取，`limit=1000`；
- 瓦片缓存 30 天，单小区缓存 30 天，**未命中（查不到）缓存 7 天**；
- 内存 memo + inflight 去重，同一批瓦片并发只打一次上游；
- **每日上游上限 4500 次**（免费额度 5000，留 500 余量），按 UTC 日期重置，`/api/cells/stats` 可查；
- 缓存落盘 `data/cells/tile/*.json` 与 `data/cells/single/*.json`（ECS 上是 `/opt/weilie/data/cells/`）。

### 密钥（不入库、不下发 App）

读取顺序：`OPENCELLID_KEY` 环境变量 → `-Dopencellid.key` → `data/cells/opencellid.key` 文件。

ECS 上已按文件方式配置：

```bash
/opt/weilie/data/cells/opencellid.key   # 权限 600，目录 700
```

App 只跟自己的服务端说话，API Key 永远不出服务器。

### 部署

```powershell
$env:JAVA_HOME='C:\AndroidDev\jdk-17.0.2'
C:\AndroidDev\gradle-8.9\bin\gradle.bat -p weilie\server test fatJar
```

产物 `weilie\server\build\libs\weilie-server-all.jar` → 覆盖 `/opt/weilie/weilie-server-all.jar` → `systemctl restart weilie.service`。

## 三、App 端

### 1. 地图图层

图层面板 →「叠加图层」→ **基站库（OpenCelliD）** 开关：

- 打开后按当前地图中心自动查询半径 900 m 内最多 100 个基站（防抖 800 ms，跟随地图平移/缩放刷新）；
- 基站按制式着色：**4G LTE 青蓝、5G NR 紫、2G GSM 橙、3G 绿、未知灰**，点中心显示制式短标签（4G/5G/2G/3G）；
- 点击任一基站 → 详情卡：运营商、制式、`MCC-MNC · LAC/TAC · CID`、十六进制 CI、坐标、精度文案、覆盖半径、距我多远，底部「导航到此」（唤起高德/百度等地图应用）与署名；
- 面板上同时显示"范围内 N 个 · 点此重新查询"，以及众包精度与许可提示。

### 2. 查询弹窗

两个 tab：

- **附近基站**：填纬度/经度（默认取当前位置或目标中心）+ 半径药丸（300 m / 500 m / 900 m / 1.5 km / 2.5 km）；
- **按编号查询**：填 `MCC`、`MNC`、`LAC/TAC`、`CellID`，例如 `460 / 0 / 4213 / 18712839`。

查到后点一行即选中：地图聚焦到该点，并弹同一个详情卡。

> 匹配键说明：LTE 的 `ECI` 与库里的 `cellid` 是同一个 28 bit 编号，`TAC` 对应 `lac`，可直接查；
> 5G NR 的 `NCI` 在库里极少；**邻区只有 PCI + EARFCN，库里不存 PCI，无法给单个邻区定位**，所以邻区只能在"附近基站"里整体看。

### 3. 队长按基站为中心划区

多人房间 → 任务面板 →「**以基站为中心划区（搜索基站位置）**」：

1. 搜到目标基站（或用附近基站挑一个）；
2. 选择切分方式：
   - **按方位切扇形**：把以基站为中心的圆按参与人数等分（一人守一个方向，适合沿路推进）；
   - **按半径切圈层**：同心圈层，**等面积**切分（`第 i 层外半径 = R·√((i+1)/n)`），每人负责面积相同，适合先控中心再外扩；
3. 设半径（300–2000 m，默认 800 m）；圈层模式再设层数（2–4，默认 3）；
4. 点「下发任务区」：按参与队员（排除观战）逐块下发 `Zone(kind=POLYGON, assignees=[某队员])`，备注形如 `任务：中国移动 · 4G LTE · 扇区 2/4`。

<!-- 注意：上面这行代码块在 Markdown 渲染时按字面显示 -->
逐块下发时**只有第一块带 `replace=true`**（服务端收到它会先 `zones.clear()`），后面几块 `replace=false`；否则每一块都会清空前面的，最后只剩一块（这个坑在 v0.6.0 真机联调时被抓到并修掉）。

## 四、算法要点

| 位置 | 做法 |
| --- | --- |
| `core/cellmap/CellLibraryModels.kt` | 服务端 DTO + 派生展示属性（运营商映射、制式文案、`hexCi`、精度文案、距离）；`isValid()` 过滤脏坐标（非有限、越界、0,0） |
| `core/cellmap/CellLibraryClient.kt` | Ktor CIO 客户端；`near()`/`lookup()`/`nearCached()`（60 s 记忆化）；**任何异常都转 `ok=false` + 中文提示，不上抛** |
| `core/cellmap/SectorZones.kt` | `sectors()` 等角度扇形；`rings()` **等面积**圈层；`circle()`；`areaM2()` 局部平面鞋带公式；`labelFor()` 生成"扇区 i/N / 圈层 i/N" |
| `ui/map/CellLibraryStyle.kt` | 制式配色与短标签的**单一来源**（地图引擎、Canvas 兜底、查询弹窗共用） |
| `ui/map/BaiduMapCanvas.kt` | 基站用 `Marker`（`clickable(true)`）+ `IdentityHashMap` 反查，最多画 200 个（超出等步长抽稀）；渲染指纹纳入 `selectedCellKey` 与每个站的 `key/lat/lon`，避免"数据变了不重绘" |
| `ui/map/MapCanvas.kt` | Canvas 兜底路径同样画基站、且点选命中**基站优先于普通地图点选** |
| `ui/map/SingleMapScreen.kt` | 图层状态 + 防抖拉取 + 选中详情卡 + 导出图图例补"基站库" |
| `ui/team/TeamRoomScreen.kt` | 队长搜站 → 选切分方式/半径/层数 → 逐块 `WsMsg.Zone` 下发；基站中心以本地 marker 显示 |

> 关于 `metersPerDegLon`：实现是 `(111320 × cos(lat)).coerceAtLeast(1.0)`。
> v0.6.0 开发中 Unit Test 抓到一个真实 bug——原先写成 `111320 × cos(...).coerceAtLeast(1.0)`，
> 括号位置错导致 cos 项被强制为 1.0，经度方向距离恒等于纬度方向（北京地区偏大约 30%）。已修，并由 `CellLibraryModelsTest` 守住。

## 五、验收清单（真机）

1. 图层面板出现「基站库（OpenCelliD）」；打开后地图上出现若干彩色基站标记（城市区域应有数据）。
2. 点一个基站 → 详情卡信息完整，点「导航到此」能唤起地图应用。
3. 面板「点此查询基站位置」→ 弹窗「附近基站」能出列表；切到「按编号查询」填 `460 / 0 / 4213 / 18712839` 能查到北京那个点。
4. 移动地图（平移/缩放）→ 基站列表跟着刷新，不会一直卡在旧位置。
5. 关掉开关 → 标记消失；再打开 → 重新出现。
6. 多人房间：队长 → 任务面板 →「以基站为中心划区」→ 搜站 → 扇形/圈层各试一次 → 队员端能看到分配给自己的多边形区块，备注含基站名与"扇区/圈层 i/N"。
7. 观战成员不参与分配；只有 1 名队员时扇形退化为整圆。
8. 导出轨迹图，图例里有"基站库"一项（开关打开且查到数据时）。

## 七、已知限制

- OpenCelliD 在中国的数据密度有限，**不是"全部基站"**；用户真机上那个目标小区（460-01 / TAC 4308 / ECI 240606319）在该区域就查不到。功能定位是"参考图层"，不替代实测。
- 免费额度 5000 次/天，服务端已加 4500 次/天的自限 + 30 天瓦片缓存；瓦片粒度 0.018°，越界查询会补齐相邻瓦片，单次最多 4 次上游调用。
- 5G NR 站点在库中占比极低，按 NCI 查大概率查不到。
- 邻区（只有 PCI+EARFCN）无法单点定位，只能"附近基站"整体展示。
- 基站库坐标不能作为执法依据，只能作为搜捕路线规划与设备调度的参考；正式取证仍走 App 内的实测采样 + 水印相机 + 在线验真链路。
